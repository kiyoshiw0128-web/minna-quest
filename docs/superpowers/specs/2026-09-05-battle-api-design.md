# 段階3c — 戦闘API設計

## 1. この段階のゴール

**戦闘が成立する。** その日のイベントが戦闘なら、8ターンのプランを組んでサーバに送り、
サーバが `simulate` を回して結果を返す。勝てば報酬が入る。

全体設計（`2026-09-03-minna-quest-design.md`）の §5.5 と §7 を引き継ぐ。
そこで決まっていることは蒸し返さない。

## 2. なぜ雇用まで含めるか

戦闘だけ足しても**主人公1人では章ボスに勝てない**。バルゴスはHP3747で、
パーティ戦を前提に調整した値である。1人で挑ませると、負けても罰は無いとはいえ
「勝てない戦いを繰り返す」だけになる。

したがってこの段階は「戦いが成立するのに要るもの」までを範囲とする。
キャラクターの永続化、金貨、酒場での雇用、戦闘。この4つで1組。

**先送りするもの:** ペット、装備品、転職API、装備枠の変更API。
いずれも無くても戦えるので、段階3dに送る。

## 3. データモデル

既存5テーブルに加えて4つ。全体設計 §7.1 の名前をそのまま使う。

```
characters      id, player_id, name, adventure_level, adventure_exp,
                aptitude(JSON), current_job, gold は players 側に持つ
job_levels      character_id, job_id, level, exp        ← 二階建ての要
learned         character_id, kind('skill'|'passive'), id
party           player_id, character_id, slot(0-3)      ← 戦闘に出す並び
battle_results  world_id, day_no, player_id, result, rewarded_at
```

`players` に `gold` を足す。金貨はプレイヤー単位で持つ。キャラ単位にすると、
雇用の原資をどのキャラが持つかという問いが生まれて、得るものが無い。

**装備枠（`equippedActive` / `equippedPassive`）は `characters` にJSONで持つ。**
`learned` と分けるのは、習得は永久・装備は付け替えるものだから。

### 3.1 主人公は参加時に作る

`/api/join` が成功したとき、そのプレイヤーの主人公を1体作る。

- 職業は戦士で固定。最初の1体に選択肢を出しても判断材料が無い
- **素質は `playerId` から決定論で引く。** 乱数を使わない。同じプレイヤーIDからは
  必ず同じ素質になり、後から検証できる
- `createCharacter` が初期職の技を習得させる（core側に既にある）

### 3.2 パーティ

最大4人。参加時は主人公1人。雇用したメンバーを枠に入れる。
**枠の並びがそのまま戦闘の並び。** 行動順は速度で決まるので、並びは表示順でしかない。

## 4. 金貨

**その日の選択肢の結果（`EventOutcome.gold`）を、締めたときに世界の全員に配る。**
ルートは共有なので、得られるものも共有でよい。誰が投票したかで差をつけない。

これは `catchUp` の中で、日を締めるのと同じバッチに入れる。締めが冪等なので
配布も冪等になる。**別のバッチにすると、二重に配る事故が起きうる。**

戦闘に勝った報酬の金貨は、勝った本人だけが受け取る（§6）。

## 5. 酒場

`GET /api/tavern` — その日の3人。`rollRecruits`（core、`tavernSeed`）で引く。
**全員が同じ3人を見る。** 決定論なので、後から誰が並んでいたか再現できる。

`POST /api/hire` — `{ recruitId }`。金貨を払ってパーティに加える。

- 値段は `recruitCost`（core）。金貨が足りなければ断る
- **同じ人物を複数のプレイヤーが雇える。** 取り合いにしない。
  在庫を持たせると先着処理が要り、日をまたぐ整合も要る。得るものに対して高い
- パーティが4人埋まっていれば断る。**入れ替えAPIは段階3dに送る**
- 雇ったメンバーも `characters` に入る。主人公と同じ型なので、
  あとで転職APIを足せばそのまま転職できる

## 6. 戦闘

### 6.1 何と戦うか

`GET /api/battle` — その日の戦闘の情報。

- その日の確定した選択肢が `kind: 'battle'` でなければ、戦闘は無いと返す
- **敵の行動表をそのまま返す。** 隠さない。事前セット式のパズルとして成立させる前提
- 自分のパーティ各人の実効ステータスと、装備している技

締まっていない日には戦闘は無い。その日の選択肢が確定していないため。

### 6.2 どう戦うか

`POST /api/battle` — `{ plan: { [characterId]: (string|null)[] } }`。

サーバが `simulate` を回してログを返す。**クライアントは計算しない。**
core は決定論なので、同じプランからは必ず同じログが出る。

- **何度でも挑み直せる**（全体設計 §5.5）。挑戦の回数を記録しない
- 勝った場合のみ `battle_results` に記録する。**すでに勝っている日は上書きしない**
- 持っていない技を指すプランは、core が `unknownSkill` として記録する。
  **弾かずに記録する。** サーバが正なので、壊れたプランは負けとして扱えばよい

### 6.3 世界としての討伐

`world_days` に `defeated_by` を足す。**最初に勝ったプレイヤーのID。**
`UPDATE ... WHERE defeated_by IS NULL` で守る。締めと同じ形で冪等にする。

誰かが倒せば世界としては討伐済み。ただし**報酬は勝った本人だけ**（全体設計 §5.5）。

### 6.4 報酬

勝ったとき、初回のみ。

- パーティ全員に経験値。`gainExp`（core）が冒険レベルとジョブレベルの両方を進める
- プレイヤーに金貨
- 量は敵の強さから決める。**マスタに書く。**サーバのコードに数値を埋めない

`battle_results.rewarded_at` が入っていれば二度目は配らない。
**報酬の付与と `battle_results` の更新は同じバッチに入れる。**
分けると、経験値だけ入って記録が残らない、あるいはその逆が起きる。

## 7. 触らないもの

- **既存の4本のAPIの応答を変えない。** 画面が動かなくなる
- **`packages/core` を変えない。** 必要な関数はすべて既にある
- **`data/events.ts` を変えない**（追記のみの表）

## 8. テスト

`apps/worker` の既存の枠組み（本物の workerd と D1）で書く。

**必ず見るもの。**

1. 参加すると主人公が1体でき、初期職の技を習得している
2. 同じ `playerId` からは必ず同じ素質が出る（決定論）
3. 締めたとき、選択肢の `gold` が世界の全員に入る。**二重に締めても二重に入らない**
4. 酒場は全員に同じ3人を見せる
5. 金貨が足りなければ雇えない。パーティが埋まっていれば雇えない
6. 戦闘が無い日に `POST /api/battle` は断られる
7. 同じプランからは同じログが出る（決定論）
8. **勝っても2回目の報酬は入らない**
9. **2人が同じ日に勝ったとき、`defeated_by` は最初の1人のまま動かない**
10. 持っていない技を指すプランが、弾かれずに `unknownSkill` として記録される

**結果ではなく仕組みを見ること。** 「勝てる」ではなく「この条件でこう記録される」を
検査する。特に 3・8・9 は冪等性の検査なので、ガードを外すと落ちることを確かめること。

## 9. 段階3dに送るもの

ペット、装備品、転職API、装備枠の変更API、パーティの入れ替え、
雇用したメンバーの解雇。いずれも戦闘の成立には要らない。
