# 段階4a — 画面（毎日の投票ループ）設計

## 1. この段階で作るもの

**毎日の投票ループを、人が触れる形にする。** 招待コードで参加し、その日の3択を見て投票し、
締まった結果と世界の履歴を見る。ここまで。

## 2. この段階で作らないもの（と、その理由）

**戦闘の画面は作らない。** 戦闘APIが存在しないため。いま画面だけ作っても、
存在しないエンドポイントに向かって組むことになる。戦闘は段階3cでサーバを足してから。

パーティ編成・酒場・転職の画面も同じ理由で作らない。エンジンには仕組みがあるが、
サーバに永続化と API が無い。

**結果として、この段階を終えても「戦って勝つ」体験は無い。** 得られるのは
「毎日ログインして、みんなで行き先を決め、翌朝に決まっているのを見る」ところまで。
毎日の周回そのものが成立するので、サーバが本当に動いていることが目で確かめられる。

## 3. 構成

```
apps/web/     新規。Vite + React + TypeScript
apps/worker/  既存。ここに静的アセットの配信を足す
packages/core 既存。イベント名の解決に使う（変更しない）
```

### 同じ Worker から配信する

`apps/web` のビルド成果物を `apps/worker` の静的アセットとして配信する。
別ドメインに置かない。理由は3つ。

- **CORS が要らない。** 画面と API が同一オリジンになる
- **デプロイが1回で済む。** `wrangler deploy` だけ。手順が増えない
- **トークンの置き場所が素直になる。** 別オリジンだと Cookie も localStorage も面倒になる

`/api/*` は既存のルーティングが先に処理し、それ以外を静的アセットに落とす。
SPA なので、見つからないパスは `index.html` に返す。

### API は変更しない

既存の4本（`/api/join` `/api/today` `/api/vote` `/api/world`）だけで、この段階の画面は成立する。
**サーバに手を入れるのは静的アセットの配信を足す1点のみ。**

### イベント名は画面側で解決する

API が返すのは `optionIds`（イベントID）だけで、名前は含まない。
画面が `@mq/core` の `EVENTS` を読んで名前と種別（戦闘か出来事か）を引く。

これで API を変えずに済む。マスタは静的なので、画面のバンドルに含めて問題ない。
**IDに対応するイベントが `EVENTS` に無い場合は、IDをそのまま表示する。**
黙って空欄にすると、マスタと世界の食い違いが見えなくなる。

## 4. 画面

3つ。ルーティングはパスではなく状態で切り替える（履歴を扱わない小さなアプリなので）。

### 4.1 参加（未認証のとき）

招待コードと名前を入れて `/api/join` を叩く。成功したらトークンを `localStorage` に保存し、
今日の画面へ移る。

- コードが無効・使用済みのときは、その旨をそのまま出す。**どちらであるかは区別しない**
  （サーバが区別していない。総当たりの手がかりを与えないため）
- 名前は空を弾く。前後の空白は落とす

### 4.2 今日（認証済み・その日が未締め）

- 何日目か、第何章か
- 3つの選択肢。それぞれ名前と、戦闘か出来事かの区別
- 自分が投票済みならその選択肢を強調する。**投票は変更できる**（サーバが upsert する）
- **票数は出さない。** サーバが締めるまで返さないため。「まだ分からない」と明示する
- 次に締まる時刻（毎朝5時）を書いておく

### 4.3 今日（締め済み）

その日が締まっている場合、`/api/today` は `chosenId`・`counts`・`tiebroken` を返す。

- 決まった選択肢を大きく出す
- 選択肢ごとの票数
- 同数でシードで決まった場合はそう書く。**隠さない**（決定論であることが売りなので）

### 4.4 世界の履歴

`/api/world` の内容。世界の名前、いま何日目か、第何章か、獲得しているタグ、
締まった日の一覧（日ごとに、何が選ばれ、票がどう割れたか）。

タグは「通ってきたルート」の可視化なので、そのまま列挙する。

## 5. 状態と保存

- **トークンは `localStorage` に置く。** 身内数人が使うものなので、これで足りる
- トークンが無ければ参加画面。あれば今日の画面
- `401` が返ったらトークンを捨てて参加画面に戻す。**黙って失敗させない**
- 画面の状態はコンポーネントの `useState` で持つ。状態管理ライブラリは入れない

## 6. 失敗の扱い

**通信の失敗を握り潰さない。** 4つのAPIすべてについて、
「読み込み中」「失敗した（理由つき）」「再試行」を出す。

サーバの応答は `{ ok: true, ... }` か `{ ok: false, error: string }`（既存の `respond.ts`）。
`error` はそのまま画面に出してよい文言になっている。

締め切りとの競合（投票しようとしたら締まっていた）は、サーバが
`this day is already closed` を返す。**その場合は今日の画面を読み直す。**
エラーだけ出して古い画面を残さない。

## 7. テスト

Vitest + Testing Library。**サーバは本物を叩かず、`fetch` を差し替える。**

見るべきもの。

1. トークンが無ければ参加画面、あれば今日の画面が出る
2. 招待コードが無効なとき、その旨が出て、トークンが保存されない
3. 未締めの日で票数が画面に出ない（**結果ではなく仕組みを見る**。
   `counts` を含む応答を渡しても票数が出ないこと、ではなく、
   `counts: null` の応答で「まだ分からない」と出ること）
4. 投票済みの選択肢が強調される
5. 締め済みの日で、決まった選択肢と票数が出る。同数だった場合その旨が出る
6. `401` でトークンが捨てられ、参加画面に戻る
7. 投票が「締め済み」で弾かれたとき、今日の画面が読み直される
8. `EVENTS` に無いIDが来たとき、IDがそのまま出る

**E2E は入れない。** ブラウザ実行の基盤が無く、この規模では割に合わない。

## 8. やらないと決めたこと

- **状態管理ライブラリ・UIフレームワーク・CSSフレームワークを入れない。** 画面3つに対して重い
- **ルーティングライブラリを入れない。** URLを持たないので不要
- **見た目の作り込みをしない。** 読める・押せる・今どうなっているか分かる、まで
- **オフライン対応・PWA化をしない**
