# みんなクエスト（仮） 設計書

作成日: 2026-09-03
ステータス: 設計確定・実装計画待ち

## 1. これは何か

身内数人で遊ぶ、デイリー制のブラウザRPG。

一言でいうと **「物語は全員で共有し、戦力は各自で育てる」** ゲーム。

毎日、全員が「明日どこへ向かうか」を投票し、多数決で世界のルートが決まる。
決まったルートで起きる出来事（イベント・ボス戦）は全員に共通で降りかかるが、
それに挑むパーティは各プレイヤーが自分で編成した固有のもの。

同じ問題を別々の編成で解くので、「昨日の竜、どう組んだ？」が自然な会話になる。

### 中核となる遊び

戦闘は **完全事前セット式**。戦闘が始まる前に、各キャラの1〜8ターン目の行動を
すべて並べておき、あとは自動再生を見守る。乱数は一切ない。敵の行動表も事前に
全部公開されている。つまり戦闘は運試しではなく **解けるパズル** であり、
負けたら並びを組み替えて解き直す。

### 設計の前提（確定済み）

| 項目 | 決定 |
|---|---|
| 時間軸 | 現実の1日 = ゲームの1日（デイリー制） |
| 実行環境 | Cloudflare 上の Web アプリ。身内向け |
| 戦闘 | 完全事前セット（プログラミング型）、乱数ゼロ |
| シナリオ | イベントプールからのシード抽選 |
| 死の扱い | キャラは死なない。敗北はペナルティのみ |
| 共有範囲 | ルートは共有、戦闘は各自 |
| 進行ペース | 毎日 JST 05:00 固定で締める |

## 2. アーキテクチャ

### 2.1 Cloudflare 構成

Worker を1つだけ立て、そこに全部を載せる。Pages は使わず
Workers Static Assets でフロントを配信する。API とフロントが同一オリジンに
なるため、CORS も環境変数の二重管理も発生しない。

- **Worker** — API・静的配信・Cron Trigger
- **D1** — 世界の進行と全プレイヤーのセーブ
- **Cron Trigger** — 毎日 JST 05:00 に投票を締めてルートを確定

### 2.2 リポジトリ構成

```
packages/core/     ゲームロジック（純TS・依存ゼロ・Vitest）
  battle/          simulate(party, enemy, plan) -> BattleLog
  progression/     経験値・職業・上級職・スキル習得
  events/          イベント抽選（シードから決定論的に）
  data/            マスタデータ（技・職業・敵・イベント）
apps/worker/       Worker（API・D1・Cron）。core を import
apps/web/          Vite + React。core を import（プレビュー計算のみ）
```

### 2.3 戦闘はサーバが回す

完全事前セット式なので、戦闘の入力は「編成 + 技の並び + シード」だけ。
したがってクライアントは `plan` を POST するだけでよく、Worker が `core` で
戦闘を解決し、`BattleLog`（全ターンの記録）を返す。フロントはそれを再生する。

この形にする理由:

1. 経験値や資金の改ざんが構造的に起きない（結果をクライアントに作らせないため）
2. UI が薄くなる。フロントは再生装置に徹する
3. `core` が純関数なので、ブラウザを起動せずに Vitest でボス調整ができる

ただし **プラン編集画面のダメージプレビュー** のため、フロントも `core` を
import する。`core` は依存ゼロの純TSなので同じコードがブラウザで動く。
サーバが正である点は変わらない（確定結果は必ずサーバの `simulate` が返す）。

### 2.4 認証と日付

- **認証** — 身内前提。招待コード + ブラウザ保存トークンのみ。
  アカウント登録もパスワードも作らない。
- **日付** — Worker 側の JST 固定。端末の時計は一切参照しない。

## 3. 戦闘エンジン

### 3.1 乱数ゼロと行動表の公開

命中率もダメージ幅も持たない。完全事前セット式で乱数があると、同じプランが
勝ったり負けたりして「考えて解いた」感触が消えるため。

乱数の代わりに、**敵の行動表を事前に全部公開する**。

```
【炎竜バルゴス】HP 320  速度 12  DEF 60  MDF 40  ATK 24  MAT 22
 1T 火炎の息   全体 魔法 威力180
 2T 威嚇       全体の攻撃力 -30%（3T）
 3T 溜め       行動なし・被ダメ +50%
 4T 灼熱爆発   全体 魔法 威力900
 ※HP 50% 以下で「激昂」— 以降 行動表が B に切り替わる
```

> **2026-09-05 改訂。** バルゴスのHPは当初4800としていたが、これは育ちきった
> パーティ（冒険Lv50想定）を基準にした数値だった。章ボスは7日目に来る。
> 雑魚の報酬から逆算すると7日目のプレイヤーは冒険Lv2〜3・金貨135〜250で、
> 雇えるのは1〜2人であり、誰にも倒せない壁になっていた。世界は誰か1人が
> 倒せば進むが、その1人が存在しなかった。
>
> HP 320・攻撃 24・魔力 22 に引き下げた。Lv3が3人の素朴な並びで勝て、
> Lv3が1人またはLv2が3人では勝てない水準として実測で決めている。
>
> **副作用として、上の「溜めの窓に大技を集中させる」想定解は第1章では
> 成立しなくなった。** 7日目のプレイヤーは、窓に叩き込む大技をまだ覚えていない。
> パズルとしての手応えは、技が揃う第2章以降のボスで作る必要がある。
> 第2章以降のボスはまだ存在しない。

読めるからこそ「3ターン目に火力を全部ぶつける」「2ターン目の威嚇の前に
殴り切る」という解が生まれる。

### 3.2 プランの形

パーティは最大4人（主人公 + 雇用メンバー3）+ ペット1体。
各キャラに最大8ターン分の行動を並べる。制約は3つ:

- **MP 総量** — 強い技を序盤に積むと後半が空になる
- **クールダウン** — 同じ技は N ターン空ける
- **行動順** — 速度順で解決。速度は職業と装備で動くため、
  行動順そのものが攻略要素になる（バフを敵の攻撃より先に置けるか）

### 3.3 ダメージ計算

技を4タイプに分ける。

| タイプ | 計算 | 役割 |
|---|---|---|
| 物理 | ATK と DEF で計算 | 主力。高防御に弱い |
| 魔法 | MAT と MDF で計算 | DEF が高い敵への回答 |
| 固定 | 防御を見ない定数 | 硬すぎる相手を削る保険。伸びないので終盤の主力にはならない |
| 割合 | 敵の最大HPの x%（上限あり） | 高HPボス専用。雑魚には効かない |

計算式（除算式）:

```
基礎   = ATK × 技威力 / 100
軽減後 = 基礎 × 100 / (100 + DEF)
最終   = floor( 軽減後 × 属性倍率 × バフ倍率 × 被ダメ倍率 )   ※最低1
```

減算式（`ATK − DEF`）は数値が読みやすい代わりに、防御が少し上がっただけで
ダメージがゼロに落ちて詰みが生まれる。除算式は極端に壊れないためボス調整が楽。

この式により、防御を下げる／貫通する選択肢が戦術として意味を持つ:

- 防御ダウンのデバフ（3ターン DEF −40%）
- 貫通率つきの技（DEF を 50% として計算）
- 「溜め」中の被ダメ +50% を狙って火力を置く

除算式は暗算しづらいため、プラン編集画面に **ダメージプレビュー** を出す。

### 3.4 解決の流れ

```ts
simulate(party, enemy, plan) -> BattleLog
```

1ターン = 全キャラと敵を速度順に並べ、上から解決する。各ステップを
`BattleLog` に積む。フロントはこのログを再生するだけ。

### 3.5 ペット

技を持たず、**常時パッシブのみ**（例:「毎ターン HP 回復」「味方全体の速度 +2」）。
プランのスロットを増やすと UI も攻略も一気に重くなるため、
ペットは編成段階の選択で完結させる。1体だけ連れて行ける。

### 3.6 シードの用途

シードは **戦闘には使わない**。使うのは「その日のイベント抽選」と
「酒場に誰が並ぶか」だけ。

## 4. 育成

### 4.1 レベルの二階建て

パーティ4人全員が同じ仕組みで動く。主人公は「外せない1人目」であるだけで、
システム上の特別扱いはない（`core/progression` が1種類のキャラを扱えばよくなる）。

- **冒険レベル** — 冒険日数と戦闘で上がる。HP・MP・基礎ステータスを決める。
  **転職しても絶対に下がらない**
- **ジョブレベル** — その職業で戦った分だけ、職業ごとに独立して上がる。
  ステータス補正とスキル習得を決める

DQ3 式の「転職 = レベル1に戻る」は、1日1戦しか進まないデイリー制では
転職が事実上の自殺になるため採らない。分けておけば、いつでも気軽に職業を試せる。

### 4.2 スキルは習得と装備を分ける

ジョブレベルで習得した技は **永久に消えない**。ただし戦闘に持ち込めるのは
**アクティブ6枠 + パッシブ2枠**。

これにより「戦士で覚えた挑発を、魔法使いに転職した今も1枠だけ持っていく」
ができる。この枠の取り合いが編成の面白さになる。

### 4.3 上級職

複合条件で解禁する。全キャラ共通の条件。

```
パラディン ← 戦士 Lv20 + 僧侶 Lv15
魔剣士     ← 戦士 Lv15 + 魔法使い Lv20
```

上級職は「寄り道して複数の職業を育てた人へのご褒美」。デイリー制で日数が
かかるため、長期目標として機能する。

### 4.4 雇用メンバー

酒場に日替わりで3人並ぶ（その日のシードで決定論的に生成。全員が同じ顔ぶれを見る）。
雇用は一括の金貨払い。雇用枠は3（主人公と合わせてパーティ4人）。
解雇は自由だが金は戻らない。

メンバーも **主人公と同様に転職でき、ジョブレベルで技を覚える**。
したがって酒場に並ぶ職業は初期値でしかない。差がつくポイントは2つ:

1. **素質（成長率）** — 個体ごとに「力 A / 素早さ C / 魔力 D」のような成長率。
   転職しても変わらない、その人物の地力。魔力 A の人材は将来の賢者候補
2. **冒険レベル** — 加入時点の冒険レベル。低いと安いが育てるのに日数がかかる。
   デイリー制なので日数がそのままコスト

「安いけど Lv3 の素質A」と「高いけど Lv15 の素質C」を天秤にかける、という
判断が毎日発生する。

### 4.5 ペットの入手

**買えない。イベント報酬のみ。** 金で解決できない要素を1つ残すことで、
イベント選択に重みが出る。

## 5. 日次ループ

### 5.1 プレイヤー視点の1日

```
開く → (1) 今日の出来事を見る（昨日の多数決の結果）
      → (2) 対処する（戦闘 or 非戦闘イベント）
      → (3) 明日の選択肢に投票する
      → 必要なら編成・転職をいじる
```

必須は (2) と (3) だけなので、日々のプレイは1〜2分で終わる。

(2) の中身は日によって変わる。**ボスの日は章ボス戦、それ以外の日は雑魚戦か
非戦闘イベント**（分かれ道、交渉、休息など）。非戦闘イベントは戦闘を伴わず、
金貨・フラグ・ペットなどを与えて終わる。雑魚戦もボス戦と同じ事前セット式だが、
敵が弱く行動表も短いため、プランを作り直さずに前日の並びを使い回せる。

### 5.2 Cron が回すこと（JST 05:00）

1. 前日の投票を集計し、最多得票の選択肢を確定
2. 同票なら `hash(worldId, day_no)` で決定論的にタイブレーク
   （サイコロを振らないので後から検証できる）
3. 確定した選択肢と現在のフラグから、次の日のイベントを抽選
4. 新しい3択を提示

**冪等性が必須。** 締め処理が失敗すると世界が止まるため、同じ `day_no` を
二重に締めても結果が変わらないように作る。締めていない日が複数あれば、
次回実行時に古い順にすべて処理して取り戻す。

### 5.3 イベント抽選

```ts
pickEvents(pool, flags, seed) -> [Option, Option, Option]
```

`flags` は世界の状態（現在の章、通ってきたルート、獲得済みフラグ）。
プールの各イベントは出現条件を持ち、条件を満たすものからシードで3つ引く。
シードが共通なので **全員が同じ3択を見る**。決定論であることにより
「なぜこの選択肢が出たか」を後から再現できる。

### 5.4 投票の可視性

締めた後に「7人中4人が森を選んだ」と表示する。**締める前は非公開**。
先に見えると後から投票する人が流されるため。

### 5.5 ボスと敗北の扱い

7日ごとに章ボス。ボスは全員共通で、各自が自分の編成で挑む。

**ボス戦は当日中なら何度でも挑み直せる。** 完全事前セット式＝パズルなので、
負けたら並びを組み替えて即リトライできるのが自然。

**世界の時計は止まらない。誰か1人でも倒せば、そのボスは討伐扱いとなる。**

これは「全員がひとつの一団の仲間である」という設定に基づく。誰かが炎竜を
斬ったなら炎竜は死んだのであり、自分が倒せなかったのは
「その戦いで自分は力になれなかった」というだけ。物語の矛盾は生じない。

したがって用語も「未討伐（敗北記録）」ではなく **「討伐に貢献できなかった」** とする。

- **報酬は貢献した人だけが受け取る。** 倒せなかった人は経験値も戦利品も得られない
- 後日その戦いに挑むのは「宿題」ではなく **追体験**。勝てば報酬は入る
- ただし **初撃破の称号は最初に倒した人のもの**

これにより、遅れても追いつけるが、その日倒した人はきちんと報われる。
罰ではなく差がつくだけ、という形になる。1週間離れていた人も、戻ってきて
溜まったボスを順に片付ければ追いつける。

### 5.6 人数によるスケール

1人でも成立する。多数決の母数が1人なら自分の票がそのまま通る。
人が増えると「自分の推した道が通らない」が起き始め、そこで共有の意味が出る。
人数に応じてゲームが壊れない構造になっている。

## 6. 画面

3画面のみ。

| 画面 | いつ触るか | 内容 |
|---|---|---|
| **今日** | 毎日 | 出来事を読む → 戦う → 明日に投票する |
| **戦術** | 戦う前 | 8ターン分の技を並べる。ダメージプレビュー付き |
| **編成** | 雇用・転職・スキル枠をいじった日だけ | パーティ管理 |

日々の導線は「今日」だけで完結し、「編成」は必要な日にだけ開く。
4人 × 職業管理 × 8枠 × 8ターンという情報量の重さを、この分離で隔離する。

## 7. データモデル

### 7.1 D1 のテーブル

```
worlds          世界の進行度・現在の章・フラグ
world_days      day_no・確定した選択肢・ボス・シード
votes           day_no × player × 選んだ選択肢
players         名前・招待トークン
characters      player × 冒険Lv × 現職 × 素質 × 装備枠
job_levels      character × 職業 × ジョブLv        ← 二階建ての要
learned_skills  character × 習得済みスキル
pets            character が連れているペット
hires           player が雇用しているメンバー
battle_results  player × day_no × 勝敗 × 報酬受領済みか
```

### 7.2 マスタデータの置き場所

技・職業・敵・イベントのマスタは **D1 に入れず、`packages/core` の中に
TypeScript の定数として置く**。理由:

- 型チェックが効く
- バランス調整が git の差分として見える
- テストから直接参照できる

## 8. テスト方針

`core` は依存ゼロの純関数なので、テストはここに厚く書く。

- **`simulate()` のスナップショットテスト** — ボスごとに「この編成・この並びなら
  勝てる」を固定する。バランス調整で意図せず壊れたら落ちる
- **`pickEvents()` の決定論テスト** — 同じシードなら必ず同じ3択
- **昇級条件・スキル習得の境界値テスト**
- **Worker 側の統合テスト** — D1 のマイグレーションと締め処理（cron）。
  特に締め処理の冪等性は明示的にテストする

## 9. 実装の分割

丸ごと1本の実装計画には収まらないため、4段階に割る。

1. **戦闘エンジン** — `core/battle`。`simulate()` とダメージ計算、状態異常、
   敵の行動表。ここだけで独立してテストできる
2. **育成** — `core/progression`。二階建てレベル、職業、スキル習得、上級職解禁
3. **日次アドベンチャー** — `core/events` + Worker の cron。投票・締め・抽選
4. **UI と永続化** — apps/web の3画面、D1 スキーマ、認証

最初の実装計画は **段階1（戦闘エンジン）** から切る。ゲームの面白さの大半が
ここに乗っており、かつサーバも DB も認証も不要な純粋なロジックであるため。

## 10. 意図的に採らなかった選択肢

- **戦闘に乱数を入れる** — パズル性が壊れるため
- **合体パーティでボスに挑む** — 「何ターン目に何をセット」の調整が
  多人数では成立しないため
- **キャラの死・ラン制** — デイリー制で育てたキャラを失う痛みが大きすぎるため
- **ボス未討伐で世界を足踏みさせる** — サボる人がいると全員が待たされるため
- **LLM によるイベント動的生成** — コスト・待ち時間・整合性崩壊のリスク
- **Supabase / 独自認証基盤** — 身内向けに対して過剰
