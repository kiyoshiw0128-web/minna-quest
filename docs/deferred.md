# 積み残し

実装とレビューで見つかったが、意図的に直さなかったもの。
該当箇所を触るときに一緒に片付ける。

## 段階1（戦闘エンジン）から

## 設計に効くもの

**`BattleState` が `enraged` と `enragedTurn` の2つを持ち、不整合を表現できる。**
`enraged: true, enragedTurn: null` は型として作れてしまい、その場合は
激昂前と同じ絶対ターンでの行動表参照に静かに戻る。現状 `checkEnrage` が
唯一の書き手なので実際には起きないが、`enragedTurn !== null` を唯一の
真実にして `enraged` を導出すべき。

**`elementRateFor` が対象に関係なく `state.enemyDef.resist` を読む。**
敵が1体である間だけ正しい。`resist` を `Combatant` の生成時に持たせるほうがよい。
複数体の敵を出す前に直す。

**`nextEnemyAction` が負のインデックスを防いでいない。**
`state.turn < enragedTurn` の手組み state で `entry.skillId` が例外を投げる。
空テーブルの場合は `null` を返すので、そちらに揃えるべき。

**`Combatant.effects` が可変配列のまま。** マスタデータは readonly 化したが、
戦闘中の状態はまだ書き換え可能。

## テストの穴

- スタンによる行動スキップが `simulate` 経由で一度も通っていない
  （`SKILLS` にも `BALGOS` にもスタンを与える技が無い）
- `expire` イベントを `simulate` のレベルで検証していない
- パッシブが戦闘の結果を変えることを検証していない（存在の確認だけ）
- `tickAll` の走査元が `state.combatants`（更新前）。各IDを1回しか触らないので
  正しいが、その不変条件に依存している

## 仕組み

**CI が無い。** マスタデータの不変性は `@ts-expect-error` で守っているが、
これは `tsc` を走らせないと効かない。`vitest` は通ってしまう。
`pnpm -r typecheck` を回す CI を置くまで、この保証は手動実行頼み。

**formatter / linter の設定が無い。** ファイルが増える前に入れるほうが安い。

## 細かいもの

- `computeDamage` の `ratio` 分岐が `finalize` を再利用していない
  （上限の適用位置が違うので、そのままでは再利用できない）
- `pickLowestHp` の `reduce` に初期値が無い（直前で空配列を弾いているので正しい）
- `decide()` は相打ちのターンを `win` と判定する（意図的、コメント済み）
- `index.ts` が `ActionResult` を export していない
- コミットメッセージが1つだけ英語（`c632671`）。他はすべて日本語
- 仕様書 3.1 の「3ターン目に火力を全部ぶつける」は、バルゴスが最も遅いため
  実際には +50% の窓が4ターン目に来る点と噛み合っていない。
  同節の「溜め中の被ダメ +50% を狙って火力を置く」が正しい記述

# 段階2（育成）から

## 型で守れていないもの

**`Character` の最上位フィールドが可変。** `adventureLevel` も `currentJob` も
`readonly` ではないので、`character.adventureLevel = 99` が型で止まらない。
`{ ...character }` で世代を作る設計上、同じオブジェクトが共有されうるため、
1回の書き込みが過去のスナップショットまで書き換える。
`JobProgress` は最終レビューを受けて readonly にしたが、こちらは手つかず。
段階4で永続化から復元するようになる前に直すのが安い。

**`gainExp` が負の経験値を弾かない。** 負の値を渡すと exp がマイナスに沈む。
段階3の報酬表は正の値しか渡さない予定だが、境界の検証としては安い保険。

**`computeStats` は `adventureLevel < 1` を想定していない。** 負の伸びになる。
今は到達できないが、永続化した JSON から復元するなら要ガード。

## テストの弱さ

- 「どのステータスも1を下回らない」テストがクランプを実際には通っていない
  （`statBonus` が負の職業が無いため）
- `applyLearns` の不変性テストが `learnedPassives` 側を assert していない
- レベル1で習得するパッシブを持つ職業がまだ無いため、装備枠の
  健全性テストのパッシブ側は今のところ `0 <= 2` を確かめているだけ

## 未配線

**`ProgressEvent` の `jobUnlocked` を誰も emit していない。** 段階3の日次報告で
「パラディンが解禁されました」を出す想定で型だけ置いてある。今は死んでいる。

## 段階2で切り出したもの

**雇用市場の生成**（酒場に日替わりで3人並ぶ）。その日のシードを必要とし、
そのシード付き乱数は段階3のイベント抽選と共有すべきなので別計画にした。
素質と冒険レベルという「差がつくポイント」の仕組み自体は段階2に入っている。

# 段階3a（日次ロジック）から

## 仕組み

**`packages/core/tsconfig.json` に `noEmit` も `outDir` も無い。** 素の `tsc` を
このパッケージで走らせると、ソースの隣に `.js` と `.d.ts` を吐く。一度それが起きて
120個の生成物が散らばり、計画の完了条件だった乱数 grep が生成物に当たって
失敗していた。今は `.gitignore` で隠しているだけなので、根本は直っていない。

**`closeDay` に `daySeed` を渡す誤用を型で防げない。** タイブレークは `voteSeed` を
使う前提だが、どちらも `number` なので取り違えても通る。渡し間違えると
タイブレークがイベント抽選と再び相関する。

## 決定論の前提（破ると過去が再現できなくなる）

**`data/events.ts` は追記のみ。** 抽選が「条件を満たすイベントの中の位置」を
引くため、削除や並べ替えをすると過去の日の3択が別物に変わる。イベントを
引退させるときは削除せず、出現条件で閉じる。ファイル冒頭にも明記してある。

**イベントIDに整数様の文字列を使わない。** オブジェクトのキーが整数に見えると
JavaScript が勝手に先頭へ並べ替えるため、投票結果を JSON にしたときの
キー順が締めた時点と後日の再計算で変わる。

## テストの弱さ

- `matchesCondition` の `tags: []` を直接通すテストが無い
- `eligibleEvents` の並び順保持が独立したテストになっていない
- `chapterOf` の第3章以降と0以下の日数を通すテストが無い（`chapterOf(0)` は 0 を返す）
- シードの名前空間の非衝突は50日しか掃引していない（32bitハッシュの衝突は原理的に残る）

## 段階3aで切り出したもの

**Cloudflare Worker / D1 / Cron Trigger**（段階3b）。この段階は「締めるとどうなるか」を
関数にしただけで、「JST 05:00 に誰が呼ぶか」は扱っていない。複数日を溜めて順に
処理する取り戻しも Worker 側。取り戻しは「選択→フラグ→翌日の抽選」の連鎖を
順に再生する必要があり、`applyOutcome` がその連鎖の一手を担う。

**`closeDay` の冪等ガードは `chosenId` しか見ない。** core では `closeDay` が唯一の
書き手で4フィールドを同時に埋めるので半端な状態は作れないが、D1 が列を
非原子的に書けば到達しうる。段階3bのトランザクション境界の問題。
